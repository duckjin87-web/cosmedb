# 데이터 모델

## 전체 구조

```
업체마스터 (vendors)
   │  1:N
   ├── 역량값 (capability_values) ──▶ 항목사전 (capability_dict)
   ├── 갱신이력 (change_log)
   ├── 조사대상 (survey_items) ──▶ 조사 (surveys)
   ├── 방문 (visits)
   └── 등록평가 (evaluations)
```

핵심은 **업체 정보를 가로 열로 늘리지 않는 것**입니다.
새 조사 항목이 생겨도 `capability_dict`에 코드 한 줄만 추가하면 되고, 값은 `capability_values`에 세로로 쌓입니다.

---

## 1. vendors — 업체마스터

한 업체당 1행. 자주 바뀌지 않는 정보만 둡니다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | text | 업체ID. `V001` 형식. 모든 테이블의 연결 키 |
| `name` | text | 기업명 |
| `biz_no` | text | 사업자번호. **매칭의 확정 키 — 최우선 확보 대상** |
| `ceo` | text | 대표자명 |
| `region` | text | 지역 (시·도) |
| `addr` | text | 주소 |
| `owner` | text | 사내 확인담당자 |
| `prog` | enum | 진행상황 · `완료` `진행중` `확인필요` `답변대기중` |
| `est` | date | 설립일 |
| `site` | url | 홈페이지 |
| `desc` | text | 기업개요 |
| `created_at` | date | 최초 등록일 |

### 향후 분리 권장 — sites (사업장)

가마·충전기·인증은 **공장 단위**인데 현재는 법인 단위로 붙어 있습니다.
공장이 둘 이상인 업체(`○○코스메틱 — 1,2공장 보유`)가 있으면 지금 구조로는 담을 수 없습니다. 업체 수가 적을 때 분리하는 것이 가장 저렴합니다.

| 필드 | 설명 |
|---|---|
| `site_id` | 사업장ID |
| `vendor_id` | 업체ID |
| `name` | 공장명 |
| `addr` | 공장 주소 |
| `is_main` | 주력 공장 여부 |

분리 후 `capability_values.site_id`가 채워지면 "3톤 가마가 어느 공장에 있는지"를 담을 수 있습니다.

## 2. capability_dict — 역량 항목 사전

조사 항목의 **마스터 목록**. 이 파일이 시스템의 뼈대입니다.
→ 전체 코드는 [CAPABILITY-DICTIONARY.md](CAPABILITY-DICTIONARY.md)

| 필드 | 설명 |
|---|---|
| `k` | 항목코드 (`EQ01`, `CE01` …) |
| `n` | 항목명 |
| `grp` | 그룹코드 (`EQ` `CE` `CP` `FM` `QA` `RK`) |
| `gn` | 그룹명 (설비 · 인증 · 캐파 · 제형 · 품질 · 리스크) |
| `t` | 값 유형 · `yn`(가능/불가) 또는 `num`(수치) |
| `u` | 단위 |
| `ttl` | 유효기간(개월) |

---

## 3. capability_values — 역량값

업체 × 항목코드마다 1행. **어느 조사에서 나온 값이든 여기에 모입니다.**

| 필드 | 설명 |
|---|---|
| `c` | 업체ID |
| `k` | 항목코드 |
| `v` | 값 |
| `s` | 출처 (`식약처 공표`, `업체 회신`, `방문 실사`, `조사 S004` …) |
| `g` | 신뢰등급 `A` `B` `C` `D` |
| `m` | 확인 시점 (개월 전) — 실제 구현에서는 `verified_at` 날짜 |

### 신선도 판정

```
verified_at + dict.ttl < 오늘  →  기한 경과 (재확인 대상)
남은 기간 3개월 이내          →  곧 만료
그 외                         →  유효
```

### 신뢰등급

| 등급 | 근거 | 예 |
|---|---|---|
| **A** | 인증서·공시 원본 | 식약처 CGMP 공표, 국민연금 가입인원 |
| **B** | 업체 서면 회신 | 문진표 회신, 메일 답변 |
| **C** | 구두·전언 | 전화 통화, 타사 담당자 전언 |
| **D** | 추정·검색 | 홈페이지 문구, 기업개요 추정 |

방문 실사(등록평가)의 목적 중 하나는 **C·D 값을 A·B로 올리는 것**입니다.

## 4. surveys / survey_items — 조사

### surveys

| 필드 | 설명 |
|---|---|
| `id` | 조사ID `S001` |
| `purpose` | 조사 목적 (예: `3톤 우원 가마`) |
| `creator` | 생성자 |
| `date` | 조사일 |
| `cols` | 이 조사에서 묻는 항목 배열 |
| `dict_codes` | 사전 항목코드 목록 (중복 판정에 사용) |

`cols[]` 한 항목의 구조:

```json
{ "key": "EQ01", "label": "유화기 최대용량",
  "type": "text", "options": [], "dictK": "EQ01" }
```

`dictK`가 있으면 완료 시 `capability_values`에 적재됩니다.
`dictK`가 `null`인 항목은 그 조사 안에서만 쓰이는 자유 항목이라 **재사용되지 않습니다.** 반복될 것 같으면 사전에 코드로 승격하세요.

### survey_items

| 필드 | 설명 |
|---|---|
| `survey_id` | 조사ID |
| `mid` | 연결된 업체ID (`null`이면 미연결) |
| `name` | 원본 업체명 (업로드 시 표기 그대로) |
| `st` | 매칭 상태 · `auto` `check` `new` |
| `ev` | 매칭 근거 배열 (`["업체명","대표자"]`) |
| `dup` | 중복 상태 · `have` `stale` `new` |
| `ans` | 답변 `{항목키: 값}` |
| `done` | 완료 여부 |

### 업체 상태 자동 판정

```
done = true                     →  완료
ans에 값이 하나라도 있음        →  진행중
아무 답변도 없음                →  조사대기
```

진행율은 **완료만** 집계합니다.

---

## 5. change_log — 갱신 이력

마스터 값이 바뀔 때마다 1행. 마스터 상세 화면에서 **최근 6개월**만 기본 노출합니다.

| 필드 | 설명 |
|---|---|
| `vendor_id` | 업체ID |
| `d` | 변경일 |
| `f` | 변경된 필드명 |
| `b` | 이전 값 |
| `a` | 새 값 |
| `s` | 출처 (조사ID, `수기 수정`, `방문 결과 반영` …) |

이전 값을 지우지 않고 남기는 이유는, **과거 자료의 오류를 나중에 추적**하기 위해서입니다.

## 6. visits — 방문예정처

1행 = 1방문 건. 한 업체가 재방문하면 행이 늘어납니다.

| 그룹 | 필드 |
|---|---|
| 고정 | `mid` `co` `st` `ev` `fix` `time` `memo` |
| ① 업체정보 | `biz` `kind` `addr` |
| ② 연락·자료 | `site` `link` `mgr` `pos` `tel` `mail` |
| ③ 일정협의 | `vend` `coop` `qa` |
| ④ 선정 | `picker` `reason` |
| ⑤ 방문 결과 | `vdone` `att` `res` `cq` `cd` |
| ⑥ 이력 | `ch` `by` `note` |

### 진행 상태 (8종)

`일정협의중` `방문예정` `방문완료` `Capa회신대기중` `등록완료` `방문취소` `등록불가` `기타`

행은 **삭제하지 않습니다.** 종결 3종(등록완료·방문취소·등록불가)은 무채색 음영과 취소선으로 가라앉습니다.
등록불가 업체를 지우면 2년 뒤 같은 업체를 또 검토하게 됩니다.

### 공통 가능일 계산

```
1단계  협생 가능일 ∩ 품보 가능일  =  부서 공통
2단계  부서 공통 ∩ 업체 가능일    =  최종 공통 가능일
```

결과가 세 가지로 갈립니다.

| 결과 | 의미 | 다음 조치 |
|---|---|---|
| 날짜 표시 | 확정 가능 | 방문일 확정 |
| 부서 일정 불일치 | 1단계에서 실패 | 협생·품보 재조정 |
| 업체 일정 불일치 | 2단계에서 실패 | 업체에 후보일 재요청 |

날짜 입력은 자유 텍스트를 허용하고 파서가 추출합니다.
`7/23~24`, `7/23~7/25`, `08월 13일`, `7/20 이후`, `장덕진·한아영 7/23~24` 모두 인식합니다.

## 7. evaluations — 등록평가

| 필드 | 설명 |
|---|---|
| `mid` | 업체ID |
| `name` `date` `time` | 업체명, 방문일시 |
| `reason` | 수배사유 (= 조사 목적) |
| `type` | 업체 유형 · `제조업체` / `충전·포장` |
| `att` | 방문자 |
| `st` | 평가 상태 |
| `score` | 총점 |

`type`은 CGMP 보유 여부로 자동 판정합니다.
`충전·포장`이면 제조관리 항목이 빠지고 70점 → 100점 환산이 적용됩니다.
